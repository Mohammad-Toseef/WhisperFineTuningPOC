## ★ TWO USER CLARIFICATIONS, folded into the plan

### 1. "Train the round-1 model, not the base model" — confirmed, and it is what the plan does
The mechanics can read the wrong way, so it is now spelled out in the plan. **base large-v3 +
round-1 adapter IS the round-1 model** — same weights, stored unmerged. The base was frozen
throughout round 1, so it is the substrate, never the thing trained; loading
`openai/whisper-large-v3` and attaching round 1's adapter reconstructs exactly the model that scored
10.50%, and at step 0 of round 2 the outputs are identical.

What *would* train the base model is the code as it stands. Verified by grep rather than by reading:
`ADAPTER_PATH` has **three references in `modal_app.py` — one definition and two WRITES**
(lines 210–211). Nothing loads it. `get_peft_model` (line 102) *creates* a fresh adapter from a
config, and LoRA inits `lora_B` to zeros, so its step-0 contribution is exactly nothing. Without the
resume change, round 2 would silently run as **base + a brand-new adapter** — the fresh-LoRA option
the user declined — and it would not error: normal loss curve, plausible WER, saved model, wrong
experiment, no artifact afterwards saying which happened.

Alternative (b) — load the **merged** `whisper-urdu-final` as the new base and attach a fresh
adapter — was considered and rejected: it stacks a second adapter's capacity (drifting from the
"keep r=32" decision), bakes round-1 knowledge into a frozen substrate, loads 6.17 GB instead of
60 MB per cold start, and leaves the final artifact dependent on shipping the merged r1 model.

### 2. Baselines — round 1 is primary, base is a secondary anchor
Terminology correction first: **WER is always computed against human reference transcripts**, never
against another model's output. So neither r1 nor base is a "reference"; both are *comparison
baselines*, and the reference text is the reviewed transcript either way.

⚠️ **Set B has NO round-1 baseline and cannot have one without a new run** — round 1's model was
never scored on any Batch-3 episode, because Batch 3 did not exist. So criterion 3 (the code-switch

⚠️ **Re-run r1 as a POSITIVE CONTROL even though 10.50% is already stored.** Change #7 modifies
`evaluate()`; reusing a stored figure silently assumes the normalizer and batching are unchanged.
Same move that caught session 014's `volume_result_stems` bug — an unchanged result proves nothing

### 🐞 FOUND WHILE BUILDING #5 — `evaluate()` would have destroyed round 1's numbers
`evaluate()` hardcoded `f"{VOLUME_PATH}/logs/eval_results.json"`, so a round-2 eval would have
**overwritten the file holding round 1's 18.57% / 10.50%** — the baseline this whole round is

Design note: per-path config keys were the alternative and were rejected. Forgetting one is silent,
and the one most likely to be forgotten — `dataset_path` — clobbers nothing; it just trains round 2

"which paths did that run actually use" is otherwise unanswerable from a finished log.

### #4 — three `raise`s, and one of them is better than planned
1. `trainable == 0` → adapter loaded FROZEN (the `inference_mode` trap).
2. no `lora_B` parameters → the load did not produce a LoRA model at all.
3. ★ **every `lora_B` tensor is zero** → a *freshly-initialised* adapter, so round 1's training was
   never loaded.

Check 3 was not in the plan and is the valuable one. A fresh LoRA has `lora_B == 0` in every layer —
exactly why a fresh adapter is a no-op at step 0 — so a **trained** adapter cannot be all-zero.
It therefore directly distinguishes "resumed round 1" from "silently started from scratch", which is
**the one failure mode a parameter count and a loss curve look identical under**, and it closes the
gap #3 could not verify locally. Gated on `resume_from`, since a fresh adapter is legitimately zero.

All three `raise RuntimeError` rather than printing — asserted in the test, because a warning in a
200-line training log is how session 014's 500-char cap went unnoticed for two sessions.

**6/6 checks pass.** Still NOT verified locally (no torch): the runtime param count and `lora_B`

**verified** as the Tier-2 full-run adapter (r=32, α=64, 6 targets) rather than the smoke test's,
so resuming is config-compatible. Its `inference_mode: true` flag is a **trap**: loading without
`is_trainable=True` trains nothing while looking successful, so the plan demands an assertion on
trainable params. And `train()` as written would **overwrite both** the adapter it resumes from
and the dataset holding the comparison eval set — fixed by writing round 2 to new volume paths
instead of renaming anything.

The eval design is the substantive design work. The 7 pinned round-1 episodes were held out of
round-1 training AND are absent from Batch 3, so they are never-trained-on for both adapters and
10.50% stays directly comparable — verified by reproducing round 1's exact bucket counts
(194/52/129). For the Batch-3 holdout, three options were measured and **Option 3
(`B3039, B3028, B3012, B3017, B3031, B3033`, 341 clips, 39% code_switch)** chosen, because
**B3039 is the corpus's only ear-verified fabrication** and reviewers corrected it into a 43-word
English reference — the single direct measurement available for blocking item #16. The accepted
cost is that 3 of the 69 sustained-English clips move from training to measurement.
