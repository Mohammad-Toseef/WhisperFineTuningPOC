# Batch 3 pipeline design (2026-08-06)

## Orchestrator decision: NOT Airflow
- **Airflow rejected**, 3 reasons: (1) no official Windows support → WSL2/Docker + scheduler +
  webserver + metadata DB just to drive a 96-video batch; (2) this is a **one-shot backfill**,
  not a recurring job — Airflow's value (cron, SLAs, date-partitioned backfill, multi-team DAG
  repo) doesn't apply; (3) **Modal already orchestrates the expensive part** (GPU fan-out via
  `.starmap`, retries, durable volumes, `--detach`) — two orchestrators = two debug surfaces.
- Artifacts are large binaries (96 mp3s, several GB) → can't ride XCom, so Airflow would only
  be tracking *state*, which a manifest file does without a Postgres instance.
- **CHOSEN: manifest-driven idempotent driver.** `batch3_state.json` holds per-video stage
  status (downloaded → trimmed → transcribed → aligned → chunked); each stage skips videos
  already past it, so a crash/network drop resumes on re-run. GPU stages on Modal `--detach`.
- If a DAG UI is wanted later: **Prefect**, not Airflow (native Windows, pip install,
  decorators wrap existing functions, result caching = free resumability).

## KEY ARCHITECTURAL FINDING — forced alignment now double-transcribes
`align_to_srt.run_pipeline` was built for **human-verified** text: step 1 runs its own throwaway
Whisper pass only to get segment boundaries, step 2 fuzzy-matches that rough text against the
human transcript to slice it into segments.

In Batch 3 there IS no human transcript — the fine-tuned model produces the text. So calling
`run_pipeline` as-is transcribes **twice per episode** (~45 hrs of redundant GPU work), and the
anchor-match reconciles text against *itself* (mapping = identity, step is pointless).

**FIX:** add an entry point that takes the fine-tuned model's segments directly and runs only
`whisperx.align()` → `flatten_words` → `group_into_cues`, bypassing `transcribe_rough` and
`map_asr_to_gt`. Cheaper, simpler, strictly more accurate. Forced alignment is still needed —
Whisper's own timestamps are coarse; wav2vec2 CTC gives precise word-level times.

`B3nnn` label a re-run could **renumber chunks and break manifest↔audio correspondence**.

### 🐞 THREE CHAINED BUGS in stage 3+4 (only the first was visible without audio)
1. **ROOT CAUSE — degenerate HF chunk timestamp.** A 53-word segment came back with a
   **2.0s window = 26.5 w/s** vs the episode's 2.16 w/s median (12×). HF's chunked
   long-form timestamps are approximate and occasionally collapse.
2. whisperx therefore **could not** fit 53 words into 2s of frames → `backtrack failed,
   resorting to original` (looks like a benign warning).
3. **`flatten_words` then silently dropped every word in that segment** — it keeps only
   words having both `start` and `end`, and a failed segment has neither.
   → **74 of 1484 words (5.0%) vanished**, showing as a 39s hole. The SRT still passed
   EVERY structural check: contiguous indices, monotonic timings, ended exactly at 825.0s.

**Fix 1 (safety net):** per-segment grouping; a segment with no timed words is kept as one
coarse cue instead of dropped, and logs a WARNING. Recovered the text (5.0% → 1.4% loss) but
stranded 53 words on a nonsense 2.0s cue — better than losing it, still poison for training.
**Fix 2 (real fix): `repair_segment_windows()`** — widen any window too short for its own
word count into the free space its neighbours leave (cap 60s; `MAX_WORDS_PER_SECOND=5.0`).
Unit-tested on the real case + 4 edge cases.

✅ **USER VERIFIED BY EAR**: cue 44's text is correct and the speech really starts at 04:06 —
confirming the window, not the transcription, was wrong.

## ⚠️ KEY LESSON — structural checks cannot catch this class of bug
The broken SRT passed contiguous-index, monotonic-timing, no-overlap and exact-end-coverage
checks. What exposed it was **words-per-second per cue vs the episode median**. Any future
QA gate must include a rate check, not just structural validation.

### 🐞 BUG 4 — segment window starting too LATE (2nd ear check)
✅ **USER VERIFIED BY EAR: 04:33–04:44 IS speech**, so the 10.5s gap was a bug. Segment 12's
HF window began at 04:44 while its speech starts ~04:33.5, so CTC crammed its opening words
into the window's tail (12 words in 1.70s, then 6 in 0.52s). The widening pass could not
catch this: segment 12's window was long *enough*, just positioned wrong.

**Fix: a gap-closing pass — and ORDER IS LOAD-BEARING.** I first wrote it to run *after*
widening, which unit-tested fine but would have been a **no-op on the real data**: widening
segment 11 out to 284.0 made it *look* contiguous with segment 12, so the closer saw gap=0.
The real gap was at the CUE level (CTC consumed only up to 273.5 of the widened window), not
the segment level. Closing must run FIRST, on original timestamps, because widening uses the
next segment's start as its ceiling. Reordering was the actual fix.
- `MAX_GAP_TO_CLOSE = 15.0` — a judgement call, not derived: above the measured 10.5s, below
  anything expected from real music. Safe because CTC *searches* the window for where words
  fall; capped because CTC must place every word somewhere inside it, so swallowing a long
  music stretch would smear words across it. Every closure is logged for auditability.

### Manifest merge semantics (user asked)
`batch_srt_prep.py` **merges into ONE manifest per `--output_dir`**; it never creates a
separate file per video. `load_existing_manifest()` reads the current entries,
`already_done` = `{Path(audio_path).parent.name}`, matching videos are **skipped** (not
re-chunked), new ones appended, whole list rewritten to the same `manifest.json`.
- Works *because* of the stable label: `make_video_id` returns `B3002_R2xPJwE5inA` from the
  filename, so the dedup key is independent of `video_index`/iteration order. On the
  `vid{NNNN}` fallback a re-run could renumber and **duplicate** a video into the manifest.
- **Additive, never subtractive**: deleting an SRT leaves its chunks in the manifest. To
  rebuild cleanly, delete `manifest.json` + `audio/<video_id>/` first. (Same trap as session
  012's 3 hand-removed faulty clips.)

## ★ AUTOMATION DRIVER BUILT — `run_batch_pipeline.py`
User's ask: no Claude session for routine runs; process arbitrary ranges, e.g. "B3003 to B3010".
```bash
python run_batch_pipeline.py --batch batch3 status
python run_batch_pipeline.py --batch batch3 run --from B3003 --to B3010
python run_batch_pipeline.py --batch batch3 run --next 8
python run_batch_pipeline.py --batch batch3 run --only B3005 --stages 5,6
python run_batch_pipeline.py --batch batch3 run --next 8 --dry-run
```
Runs stages 0→1→2→3+4→5→6, stopping on first failure with a "safe to re-run" message.
Selection: `--from/--to` (bare numbers accepted), `--next N`, `--only`, default = all pending.
Also `--stages`, `--dry-run`, `--revalidate`, `--model-path`, `--sleep`,
`--cookies-from-browser`, `--cookies`.

Design decisions:
- **Status derives from the filesystem + manifest, NOT a state file** — a state file can drift
  from disk. It therefore correctly sees work done by earlier manual runs.
- **`--next N` counts INCOMPLETE, not un-started** — finishes half-done work first.
- **Stages 5–6 are deliberately batch-wide**, not restricted to the selection: both are
  incremental, and running them over everything keeps the single manifest consistent with disk.
- **Waits for Modal rather than `--detach`** — detaching returns immediately and stages 5–6
  would run before the SRTs existed. Idempotency makes a network drop cheap instead.
- Verified: all selection modes, `--stages` subset, and rejection of bad labels / reversed
  ranges / unknown stages. **Only dry-run so far — no stage has yet executed THROUGH it.**
