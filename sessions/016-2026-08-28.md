## The gap that was real

**All four guards run before step 1.** They prove the adapter is loaded and trainable at step 0. None
of them proves it ever *moved*.

The surviving path: with `fp16: true` the gradient scaler **skips** any step whose gradients are
`inf`/`NaN`. If every step is skipped, the run produces a loss curve, three evals, and a saved adapter
**byte-identical to round 1's**. Probability is low — round 1 ran fp16 at *twice* round 2's learning
rate without trouble — but it is invisible in the artifact afterwards, which is the entire problem
with this bug class.

## The fix (#4b)

`train()` snapshots a signature of every trainable `lora_*` tensor before `trainer.train()`, compares
after, and raises if **zero** tensors changed.

Two placement decisions, both deliberate:

- **After the adapter save and commit.** Same reasoning that moved the commit before the merge in
  `3aed2e2`: a check at the end of a ~6 h run must never be able to destroy training that already
  succeeded. On a true positive nothing is lost — the adapter equals the resume source, which is
  backed up — and raising there **skips the merge**, so no "production" round-2 model is minted from
  untrained weights. An empty snapshot *warns* instead of raising: an inoperative check is not
  evidence of a bad adapter.
- **It stays quiet when `load_best_model_at_end` restores an earlier checkpoint** — those weights
  still differ from the starting point, which is the correct answer.

Live equivalent of the same signal, for the run itself: `grad_norm` every `logging_steps` (25). A run
of `0.0` or `nan` there *is* this failure happening; kill it rather than waiting for the guard.

## The bug the tests found in the fix

First version of the signature was `.float().abs().sum()`. **It is blind**, and a structural test
would never have noticed.

On a tensor with a balanced sign distribution, a uniform `+ε` cancels term-for-term in an *absolute*
sum: `|x+ε|` shrinks where `x<0` by roughly what it grows where `x>0`. A float32 sum then swallows the
remainder. A genuinely-changed tensor reads as unchanged.

Now **squared L2 in float64** — squares cannot cancel, and float64 keeps the resolution.

How it surfaced is worth recording, because it was luck sitting on top of a real defect: the
behavioural scenario "nudge one tensor by 1e-7" **passed in the scratchpad and failed once promoted
into the repo**. The `randn` was unseeded, so the answer depended on the draw. Two separate faults —
an unseeded test and a cancelling signature. The test is now seeded, and a balanced-sign tensor is
kept as an explicit regression.

## ★ MAJOR FINDING: round 1 trained only the DECODER. 41% of the adapter never learned.

Found by reading the launch log of round 2. The resume guard printed:

```
✅ resume confirmed: 320/512 lora_B tensors carry trained (non-zero) weights
```

**320, not 512.** That is not a partial success — it is an exact structural split:

- encoder: 32 layers × 6 modules (q,k,v,out,fc1,fc2) = **192**
- decoder: 32 layers × 10 (self-attn 4 + cross-attn 4 + fc1,fc2) = **320**

Verified directly against round 1's backed-up `adapter_model.safetensors`, not inferred from the
arithmetic:

| half | LoRA params | share | state after round 1 |
|---|---|---|---|
| **encoder** | 23,592,960 | **40.9%** | every `lora_B` exactly 0; every `lora_A` **still at random init** |
| decoder | 34,078,720 | 59.1% | trained |

`lora_A` still sitting at random init in all 192 encoder modules is the clincher: those weights never
received a single optimizer step. And since a module contributes `B @ A` with `B = 0`, the entire
encoder adapter contributed **exactly zero** to every forward pass. Round 1's 18.57% → 10.50% came
from decoder-only adaptation.

### Why nothing caught it

A parameter count, a loss curve, and a WER look **identical** whether the encoder learns or is inert,
because `lora_B` initialises to zeros — an untrained module contributes `0 @ A = 0`, which is exactly
what a correctly-initialised one contributes at step 0. This is the same blind spot the `lora_B`
non-zero guard was built for, one level deeper: the guard asks "did ANY tensor train", and 320 of them
had.

### Cause — confirmed by reproduction, not by reading

`enable_input_require_grads()` hooks `get_input_embeddings()`, which for Whisper is the **decoder's**
`embed_tokens`. The encoder's input is a mel spectrogram through frozen convs — data, so
`requires_grad=False`. With `gradient_checkpointing: true`, the **reentrant** checkpoint path decides
whether to build a backward graph from *the inputs of the checkpointed block*; parameters inside are
invisible to that decision. So encoder LoRA gets `grad=None`. The live round-2 log carries the tell:

```
torch/utils/checkpoint.py:92: UserWarning: None of the inputs have requires_grad=True.
Gradients will be None
```

Reproduced locally on the same graph shape (mel without grad → checkpointed encoder LoRA → decoder
LoRA → loss):

```
use_reentrant=True    encoder A grad = None      encoder B grad = None       decoder B grad = tensor
use_reentrant=False   encoder A grad = 0 @ step0 encoder B grad = tensor     decoder B grad = tensor
```

★ **`backward()` does not raise in either case.** The decoder half supplies a valid graph, so training
proceeds and the loss falls. That is precisely why round 1 looked healthy.

Fix, one line: `Seq2SeqTrainingArguments(..., gradient_checkpointing_kwargs={"use_reentrant": False})`.

### Decision: let round 2 run unchanged

Not applied mid-flight, on purpose:

1. **Comparability.** Round 2 currently differs from round 1 in data, LR and epochs. Adding "the
   encoder now trains" makes a WER change unattributable — and the r1-vs-r2 comparison is what this
   round is built to make.
2. **The stated priority is Urdu spelling, which lives in the decoder.** The lexical lever the Tier-2
   rationale rests on is the *decoder's* fc1/fc2, and it IS training. The encoder is acoustic
   adaptation; expected benefit for orthography is modest.
3. **Untested risk.** It adds 41% more learning capacity under an LR chosen for the decoder-only
   regime, raises the forgetting risk on Set A, and non-reentrant checkpointing carries extra
   saved-tensor bookkeeping that may not fit A10G 24 GB at batch 8.

So it becomes a deliberate **round-3 experiment with its own baseline**, where the effect can be
attributed. Left as an open question below rather than silently changed.

### `scripts/inspect_adapter.py` — so this is never rediscovered

Reports, per adapter, which LoRA modules are inert, split encoder/decoder, with parameter shares; and
`--compare` diffs two adapters tensor-by-tensor. That second mode is how "did this round change
anything, and where" gets answered from weights instead of from a WER delta — the intended use after
round 2 is round-1 backup vs the round-2 adapter.

Run against round 1 it reproduces the finding (`encoder 0 trained / 192 inert, 40.9%`) and names the
cause. Exit code 1 when anything is inert, so it can gate a pipeline. The `--compare` path was
negative-controlled by diffing the adapter against itself: 0 changed, 1024 identical.
