## Key Decisions

### Diagnosis: forced alignment IS being used — the WINDOWS differ, not the aligner
User asked whether round 1's forced-alignment technique is still in play. It is: both rounds
end in the identical `whisperx.load_align_model("ur")` → `whisperx.align()` wav2vec2 CTC step.
What changed is the **scaffolding** handed to it (align() does one forward pass per segment and
cannot take long audio, so window quality bounds alignment quality):

| | Round 1 (`run_pipeline`) | Batch 3 (`align_segments_to_srt`) |
|---|---|---|
| Window source | `whisperx.load_model` → **VAD**, cut at silence | HF `pipeline(chunk_length_s=28)` → **fixed 28s chunks** |
| Boundaries | pause-aligned by construction | arbitrary; timestamps quantized to whole seconds |
| Text | human-verified | fine-tuned model output |
| Aligner | wav2vec2 CTC | wav2vec2 CTC (identical) |

**Why bad windows are silent:** CTC can only place words *inside* the window it is given. It
never reports "these words aren't here" — it either fails to backtrack (no word times →
`flatten_words` drops them) or faithfully crams them in at 26 w/s. Every session-013 bug is a
wrong window, not a wrong aligner.

### 🐞 NEW: stage 5 drops a whole window on the 500-CHARACTER cap
B3001 lost zero words at chunking; B3002 lost 180. Recomputed the grouping offline — it is
exactly **one** window: **window 166, 180 words**, discarded by
`srt_audio_prep.validate_transcript`, whose rule is `len(transcript) > 500 → False`
("Likely a bad transcript"). It prints `⚠ Chunk 166 failed transcript validation, skipping`
and moves on; nothing downstream records the loss.

**This is downstream of the timing bug, not independent of it.** A ~24s window only holds 180
words when the cues inside it are compressed — the same 31-cues-over-8-w/s pathology session 013
found. So the 500-char cap is effectively an *undiagnosed canary* for bad timings: it fires on
exactly the windows the alignment got wrong, and silently deletes them instead of flagging them.

  that would ship the compressed window into training rather than dropping it.

## ★ VOLUME-WRITE BUILT — GPU results now survive a client disconnect (user decision)
User asked whether a local internet drop disrupts the Modal run. It did, and worse than
expected, so we built the fix before running B3003's GPU stage.

**The gap:** `transcribe_and_align` RETURNED the srt/text and the LOCAL entrypoint wrote
them to disk. So the local client was a single point of failure for a 20+ min GPU job.
Without `--detach` a disconnect makes Modal stop the app (work lost). *With* `--detach` the
container finishes — but the process that persists the result is gone, so the output is
discarded anyway and a re-run pays for the GPU twice. Session 013 had both halves of this
noted (`modal_align.py`'s docstring recommends `--detach`; the driver deliberately avoided
it) without noticing that neither protects the result.

**Built:**
- `RESULTS_SUBDIR = "srt_results"` + `results_dir_for(batch)` → one constant behind both the
  container path (`/data/srt_results/<batch>`) and the volume-relative read path.
- `transcribe_and_align` gains `out_stem` / `results_dir`, writes both files and calls
  `volume.commit()` **before returning**. Only on a non-empty SRT — writing an empty one
  would make fetch-first treat a failed episode as done and never retry it.
- `volume_result_stems()` / `read_volume_text()` / `save_result()` helpers.
- **Fetch-first in `transcribe_align`**: anything already on the volume is pulled and
  removed from `pending` before dispatch, logged as "Recovered N result(s) — no GPU needed".
- **New `fetch_results` entrypoint** for standalone recovery/inspection.
- **Driver now passes `--detach`** for stage 3+4. Corrects session 013's rationale for
  omitting it: `--detach` does NOT return early — the local entrypoint still runs to
  completion, so stages 5–6 still cannot start before the SRTs exist. It only changes the
  disconnect case.

### 🐞 BUG C — my own broad `except` silently disabled the whole feature
`volume_result_stems` first called `volume.reload()`. That is **container-only** — on the
client it raises `RuntimeError: reload() can only be called from within a running function`
— and the `except Exception` swallowed it, so the function returned an **empty set
unconditionally** and fetch-first would never have fired. Caught by testing against the real
volume rather than trusting the code.
**Fix:** dropped `reload()` (client-side `listdir` already queries live state) and narrowed
the catch to `modal.exception.NotFoundError`, which is the only legitimate "empty" case.
**Verified with a positive control** — an empty result from a directory with no `.srt` files
proves nothing, so re-tested the same comprehension against `model/whisper-urdu-final`:
12 entries listed, suffix filter + stem extraction correct.

### 🐞 BUG E — the Urdu aligner SILENTLY DELETES every Latin-script word
B3002's residual 4.6% word loss is **not a timing problem**. Broke the 378 missing words
down by script:

| | count | share of loss |
|---|---|---|
| LATIN | 372 | **98%** |
| digits | 6 | 2% |
| **urdu/arabic** | **0** | **0%** |

Urdu/Arabic words: 7794 in the transcript → 7794 in the SRT. **Exact match, zero lost.**
Most-dropped tokens are exactly the domain vocabulary: `energy`(13), `kinetic`(10),
`blood`(8), `Law`(6), `arteries`, `valve`, `conduction`.

**Cause:** `whisperx.load_align_model("ur")` is a wav2vec2 CTC model whose vocabulary is
Urdu/Arabic characters only. Latin letters and digits are not in it, so those words get no
timestamps, and `flatten_words` keeps only words having both `start` and `end`. The
per-segment fallback added in session 013 does not catch this — it only fires when an
ENTIRE segment is untimed, whereas this drops individual words inside otherwise-fine
segments.

**Why it was never seen before:** checked 8 round-1 episodes against their human
transcripts — **0 Latin words in the human text**, so 0 could be lost. Reviewers
transliterated everything into Nastaliq. Batch 3's machine output is the first content to
carry Latin script through this stage. Note `config/corrections.json` states the intended
policy is three-script ("English stays English, Urdu in Nastaliq, Arabic in Arabic"), which
is in direct conflict with what the aligner can represent.

**This reframes the result: with VAD, timing-caused word loss is ZERO on both episodes.**
All remaining loss is this vocabulary limitation.

**Fix (not yet implemented): interpolate timings for untimed words** rather than dropping
them — a run of untimed words sits between two timed neighbours, so their times can be
distributed across that span. Contained change in `align_segments_to_srt`. Do NOT solve it
by transliterating to Urdu before alignment: that would silently violate the three-script
policy in the training labels.

## ★★ DRIFT REPAIR BUILT AND SHIPPED — the ear-check found a bug the metrics could not
The user listened to B3002's 426.5-451.0s window and reported the deleted 9.5s contains
"form of energy is being produced" through "اب وہ جو nervous system کا جو breakdown ہوتا ہے".
That single observation reframed the problem.

### It is NOT just untimed Latin words
The last word the aligner TIMED sat at 441.5 — and it is an **Urdu** word, which CTC handles
fine. So the Latin-vocabulary gap does not merely leave Latin words untimed: **the Urdu
anchors that FOLLOW a long Latin run come back wrong too.** That breaks the fix that was
queued as PENDING #2 ("extend the interpolated run into adjacent space"): the run's right
bound IS a timed anchor, so there was nowhere to extend to. The bad anchor sits between the
run and the space it needs.

### The pattern is real, and it is code-switching-specific
| ep | VAD windows | windows leaving >1s speech uncovered at the tail | total | containing Latin |
|---|---|---|---|---|
| B3001 | 30 | 3 | 5s | **0 of 3** |
| B3002 | 121 | 14 | **51s** | **14 of 14** |
| B3003 | 149 | 5 | 9s | **5 of 5** |

Every affected window on B3002/B3003 contains Latin script. B3001 — almost no code-switching
— has three and none involve Latin. So the damage lands precisely on Urdu-English passages,
which are the hardest and most valuable examples in this speaker's material.

### Why deleted audio was the SMALLER half of the cost
Stage 5 drops the >3s holes, so ~65s never reaches training. The worse problem is the chunks
that DO ship: cue 97 was a **1.17s clip labelled with 12 English words**. That pair is not
imprecise, it is false — fine-tuning on it teaches that the sentence takes 1.17s. A deleted
chunk costs data; a mistimed chunk actively degrades the model.

### The fix — `uncovered_speech_tail` + `redistribute_over_speech`
In `align_to_srt.py`, behind a new `speech_turns` argument on `align_segments_to_srt`:
- **Detect**: compare where a segment's last word ends against where VAD says its own
  window's speech ends. >`MIN_UNCOVERED_TAIL` (1.0s) means the anchors drifted.
- **Repair**: discard EVERY CTC anchor in that segment and redistribute its words across the
  window's detected speech, weighted by character count, silences skipped so no word lands
  in a pause. All anchors go, deliberately: the drift accumulates mid-segment (cue 95 sounded
  right, cue 96 was wrong by its end), so any "last good anchor" rule is a guess.
- **Trade-off, accepted**: those segments stop being forced-aligned. Timing becomes an
  estimate (~±0.5s vs CTC's ~±0.05s), every word is marked `redistributed`, the stale CTC
  `score` is dropped, and the count/seconds recovered are logged. Right trade for chunk prep;
  worth revisiting if these SRTs are ever wanted as display subtitles.

### 🐞 BUG G — the first run produced three BYTE-IDENTICAL SRTs
`whisperx.align` **rewrites** each segment's `start`/`end` to the extent of its aligned words.
So measuring the uncovered tail against the RETURNED end is 0 by construction — the drift is
invisible exactly where it matters. Logged "No segment drifted" on all three episodes and
cost one wasted GPU run. Fixed by pairing aligned segments back to the INPUT windows by index
(with a guard + warning if the counts ever diverge). Regression test asserts both readings.
**Caught only because the cue counts did not move** — "no change" is a result to verify, not
to skim past.

Second-order effect of the same fix, and a good one: `fill_untimed_words` now also receives
the true window end, so a TRAILING untimed run extends to it instead of collapsing into the
last timed word. Several segments now repair themselves before the detector looks — which is
why the live run repaired 3/9/2 where the dry-run predicted 3/14/5. **Fewer estimates, more
CTC-accurate timings retained.**

### ★ THE DRIVER NOW KEEPS A LOG — `data/<batch>/logs/<UTC>_<batch>.log`
Stage output used to exist only in terminal scrollback. **Every defect this session was
diagnosed from a line in that output** — the cp1252 crash, the 403, "no supported JavaScript
runtime", "68 segments for 67 windows", "17 windows received more than one". A 93-video run
cannot be watched live, and the run that eventually goes wrong is the one nobody was watching.

`RunLog` is installed as `sys.stdout` (captures the driver's own prints) AND children are
piped through it (captures theirs) — both are needed, since the driver says which stage
started and the child says what happened inside it. Design points that are not obvious:
- **Raw byte chunks, not lines.** yt-dlp draws progress with `` and no newline, so
  `readline()` would block until a download finished and the log would go silent during the
  slowest stage.
- **stderr merged in** — a stage's traceback is the most valuable thing a log can hold.
- **Unbuffered.** A run that dies or is Ctrl-C'd must leave the log intact up to the point of
  death; a buffered tail discards exactly the lines that explain the failure. KeyboardInterrupt
  is recorded explicitly so an interrupt does not look like a crash.
- **Header records argv + flags in force** — six weeks on, a log cannot otherwise say whether
  `--windows vad` was used or whether the gate was overridden with `--qa-warn-only`.
- **`--dry-run` writes NO log** — it runs nothing, so a log would only look like a record of
  work that never happened.

Verified: dry-run leaves no `logs/` dir; the B3006-B3010 run produced a **167 KB** log covering
all five downloads, every VAD line, both drift repairs, the gate table and the exit footer.

⚠️ No retention policy: one log per run, growing with the batch. Under `data/`, so untracked.

## Summary
Fixed the Batch 3 timing problem that blocked session 013, and built the gate that would have
caught it. The root cause was never the forced aligner — it was **where the segment windows
were drawn**. HF's fixed 28s grid produced timestamps quantized to whole seconds and
occasionally degenerate (52 words on a 0.62s cue), and because CTC can only place words inside
the window it is handed, a misplaced window silently stranded or deleted text. Switching the
window source to **voice-activity detection** — cutting at real silences, which is what round 1
did — removed the failure mode instead of repairing it: on B3003, window repairs went 27 → 0 and
unalignable segments 3 → 0.

That exposed two further defects, both invisible to every structural check. The Urdu aligner
**silently deletes Latin-script words** (372 of 378 missing words on B3002), fixed by
interpolation. And the Urdu anchors that **follow** a Latin run are themselves wrong, stranding
whole segments ~9s early — found only because the user listened to a 9.5s stretch the pipeline
was discarding, and fixed by re-timing drifted segments against detected speech.

Final: 0.0% word loss and 98.2–99.3% coverage on all three, 492 chunks / 2.36 hrs, with a QA
gate that now scores loss against speech rather than against silence. Five of the seven bugs
found this session were in code written **during** this session; each was caught by testing
against reality — a probe, a listener, or a count that failed to move — rather than by reading
the code. The one that shipped a wasted GPU run (BUG G) was caught only because three output
files came back byte-identical.

A VAD probe confirmed the hypothesis **before** any rewrite: of the 351s B3003 was discarding,
VAD called 60% raw speech and **95% fell inside a window VAD would have built**, while still
correctly rejecting the one genuine 3.9s non-speech gap.

That work then exposed a separate, older bug: the Urdu wav2vec2 aligner's vocabulary contains no
Latin characters, so **every English word was being silently deleted** — 372 of 372 on B3002,
including `energy`, `kinetic`, `arteries` — leaving sentences as strings of stranded particles
and opening holes whose audio stage 5 then deleted as filler. Round 1 never hit it because its
human transcripts were fully transliterated into Nastaliq. Fixed by interpolating timings for
untimed words rather than dropping them.

**Result: all three episodes at 0.0% word loss, 97.5–99.2% coverage, 488 chunks / 2.34 hrs**
(up from 446 / 2.23 hrs *with* words missing), consolidated into one `Batch3` tree with
`--windows vad` as the default for the remaining 93 videos.

**Six bugs found, five silent — and three of them were in code written this session.** The
volume-write's broad `except` swallowed a container-only `reload()` and would have disabled
fetch-first entirely; the results cache keyed by stem alone would have "recovered" the chunks
output during the VAD experiment and made both paths look identical; and that same cache being
code-blind would have returned stale output after the interpolation fix. Each was caught by
testing against reality rather than trusting the code — a positive control against real volume
contents, and a probe of whisperx's actual return shape before writing the fix that depended
on it.

**The through-line, again: structural validity is not quality, and neither is any single
metric.** B3003 read a healthy 1.5% word loss while discarding 351s of speech; B3002 now reads
0.0% word loss while three cues still hold text their audio cannot contain. The QA gate exists
so the next one announces itself instead of waiting for someone to notice.
